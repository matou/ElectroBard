# M3 mobile browser audio constraints

**Question:** What can M3 rely on for Session View playback in iOS Safari and Android Chrome? This is a planning input, not a support matrix or a device test. Checked against first-party documentation and Howler's own documentation/source on 2026-09-24. The Apple, Chrome, and YouTube documentation hosts returned HTTP 403 from this research environment, so those citations identify the owning pages but could not be freshly inspected here; their precise current wording should be rechecked before treating a policy detail as a launch guarantee.

## Documented constraints

| Area | Constraint for ElectroBard | Sources |
| --- | --- | --- |
| Initial sound | Audible media and Web Audio can be blocked until a user interacts with the page. Chrome's autoplay policy allows muted autoplay, allows audible autoplay after interaction, and requires a user gesture to resume an `AudioContext` created before activation. Apple's iOS WebKit media policy likewise distinguishes user-initiated playback from autoplay. A first tap on a set tile is the natural unlock event; handle rejected `play()` / `AudioContext.resume()` and show a retry path. | [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay); [WebKit iOS media policies](https://webkit.org/blog/6784/new-video-policies-for-ios/); [Howler Mobile/Chrome Playback](https://github.com/goldfire/howler.js#mobilechrome-playback) |
| Howler unlock | Howler defaults to Web Audio and falls back to HTML5 Audio. Its `autoUnlock` is enabled by default and attempts to unlock on the first interaction; the HTML5 Audio pool is finite (`html5PoolSize` defaults to 10), since each HTML5 Audio element needs unlocking. `playerror` and `unlock` are the documented hooks for retrying a blocked start. Howler's own auto-unlock does not unlock the separate YouTube iframe player. | [Howler README: Core and Mobile/Chrome Playback](https://github.com/goldfire/howler.js/blob/master/README.md); [Howler core source](https://github.com/goldfire/howler.js/blob/master/src/howler.core.js) |
| YouTube iframe start | YouTube's IFrame API controls an embedded player separately from Howler. `playVideo()` can be blocked by the browser's autoplay policy; the API exposes `onAutoplayBlocked`. The embedding iframe should delegate `autoplay` through its `allow` attribute, but permission delegation does not replace user activation. Avoid a hidden or too-small player: YouTube's embedded-player requirements specify at least 200 × 200 pixels and no obstruction of controls where displayed. | [YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference); [YouTube embedded-player parameters and requirements](https://developers.google.com/youtube/player_parameters); [Chrome autoplay policy, iframe delegation](https://developer.chrome.com/blog/autoplay) |
| YouTube control limits | `setVolume()` accepts 0–100, `mute()`/`unMute()` are available, and `playVideo()`/`pauseVideo()`/`stopVideo()` act on the YouTube player. This is a distinct audio path from Howler's Web Audio graph; a Howler gain node cannot mix or control YouTube audio. The API documents methods for each player but makes no cross-engine synchronization or simultaneous-playback guarantee. | [YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference); [Howler README](https://github.com/goldfire/howler.js/blob/master/README.md) |
| Playback failures | YouTube's `onError` includes 100 (missing/private), 101/150 (embedding prohibited), and 153 (missing HTTP Referer or equivalent client identification). ElectroBard already treats add-time oEmbed as a heuristic. Do not set a `no-referrer` policy on the page/iframe without testing YouTube playback. Distinguish iframe errors and `onAutoplayBlocked` from Howler `playerror`. | [YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference); [ADR-0005](../adr/0005-youtube-keyless-oembed-ingestion.md) |
| HTTP and LAN | An HTTP page on a LAN can request an HTTPS YouTube iframe; this direction is not mixed content. But browser features requiring a secure context, such as service workers, do not become available on an arbitrary `http://192.168.x.x` origin merely because it is local; `localhost`/loopback is treated specially. A page served over HTTPS must avoid HTTP API/media URLs that the browser will block or upgrade as mixed content. YouTube embedding also needs network access to YouTube and its media endpoints; LAN access to ElectroBard alone is insufficient. | [MDN: Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts); [MDN: Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content); [YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference) |

## Behaviors requiring real-device checks

The cited APIs do **not** promise a uniform result for these M3 scenarios. Validate them on target iOS Safari and Android Chrome versions, with actual files and YouTube videos:

1. **First-tap path:** tap a tile before any other interaction; test file-only, YouTube-only, and a set containing both. Check whether asynchronous loading after the tap loses activation, whether each engine starts, and whether retry after `playerror` / `onAutoplayBlocked` works. Chrome documents that user activation can be delegated to an iframe, but iframe timing and iOS Safari behavior need testing.
2. **Concurrent playback:** two or more Howler sounds, YouTube plus Howler, and two YouTube players; then change per-layer volume and stop a self-stacked set. No cited source guarantees usable simultaneous mixing across engines or devices. Check audible overlap, latency, and volume behavior. YouTube's volume is separate and coarser than Howler's.
3. **Background and screen lock:** switch apps, lock the screen, return, and repeat with file-only, YouTube-only, and mixed sets. Check whether sound continues, whether timers/events pause, whether the iframe changes state, and whether the UI catches up. Browser or OS media-session behavior varies with platform, power state, and player; do not promise uninterrupted background playback from the APIs alone.
4. **Delivery topology:** test LAN HTTP by hostname and IP, and HTTPS with a same-origin API/media URL. Confirm uploaded-file range requests and playback, iframe load and `onError` 153, YouTube access on the network, and the mobile device's codec support. A local server URL being reachable does not establish YouTube availability.
5. **iOS output route:** test built-in speaker, Bluetooth, and wired output where relevant. Verify that per-layer gain remains audible and that route changes or interruptions are reflected in playback status.

## Planning implication

M3 can specify a user-initiated playback path with explicit blocked/error states. It should leave mobile concurrent mixing and background playback as acceptance risks until the device matrix above is run. Nothing in the cited browser or library APIs gives a general promise that an embedded YouTube player and uploaded-file audio will keep playing together after the screen locks.
